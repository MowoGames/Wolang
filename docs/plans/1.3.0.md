# 1.3.0

1.2.0 shipped the breaking language decisions and wrote its code before it ran
any of it. The test stage found real bugs, and CI on Linux found one more. 1.3.0
closes what 1.2.0 left open, answers the engine's wish list one decision at a
time, builds the libraries that were cut, and takes the first step of
self-hosting (D250, [self-hosting.md](self-hosting.md)).

Where 1.2.0 ended: [1.2.0-status.md](1.2.0-status.md). The engine's list:
[engine-needs.md](engine-needs.md).

## Working rules

- Build and run each step before the next one starts. 1.2.0 wrote eight
  steps blind and spent a long test stage paying for it.
- Push after every phase and read CI on every platform before the next phase.
  Windows x86-64 is the only platform a developer machine runs here.
- A language or ABI change gets its decision (D265 and up) written first, with
  the test that fails without it. Nothing in B is built before its decision is
  agreed.
- Every step ships its test, `wl fuzz 200` when it touches lowering, a back
  end, the interpreter or the runtime, and the docs and STATUS.md that agree
  with it.

## A. Close the open ends of 1.2.0

Nothing in this phase adds a feature.

1. Read CI for PR #11 on macOS and Windows arm64 (Linux is green), and fix what
   it finds. The paths never run locally: the arm64 JIT and emitter for 64-bit
   `int`, the Cocoa and Windows `gfx` and UDP code, and `aot.cc` on other
   targets.
2. Regenerate `docs/api/*.md` (they still show the old `keep` and `unsafe`
   signatures) and make `wl docs` fail when they are stale.
3. `"{MakeText()}"` leaks its temporary, because a text piece is never fresh.
4. A payload error held in a `const` before it reaches a `T!` leaks its box.
5. A name that is not imported, used as an error in a `match` arm, reports
   `E0201`. It should report an unknown name.
6. A function held in a variable and handed to a `@Thread` parameter is not
   judged by `E0147` (D252).
7. Engine item 6, live migration of host-held objects on reload. 1.2.0 refuses
   the reload with a note (D255). Migration walks the objects the host holds
   and everything reachable from globals, allocates the new layout, carries the
   fields and records old to new. It shares its machinery with serialization
   (D266), so it is built after that decision.
8. The generated binding glue registers classes without a liveness token
   (D254). The generator learns to emit one.
9. `AotTest` under `asan` on Windows: the AOT link is not given the sanitizer
   runtime. Pass it, so the one suite that is skipped runs.
10. Check the weak host slot writers (D254, D253): `object_set` and the reload
    field carry were checked by reading only. Add a test that sets a weak field
    through each path.
11. If `[]mut T` (D251) proves unstable on any platform, revert that series as
    a unit. Otherwise leave it.

## B. What the engine needs next

Each item is a decision first. The proposed answers are one paragraph each so
the owner can accept, change or drop them. **Owner** marks the ones that name
new syntax or an attribute, which only the owner decides.

- **D265, an execution budget.** The host gives a VM a budget, counted in
  ticks, and a runaway script stops instead of hanging the game thread. The
  interpreter counts loop back-edges and calls; the JIT and AOT emit a
  decrement and a branch at loop back-edges and function entry, off unless the
  budget is set. An overrun unwinds with a `BudgetExceeded` result to the host,
  and the VM stays usable. No language syntax; the API is `wolang_vm_set_budget`
  (ABI 1.4). The cost in compiled code is the thing to measure first.
- **D266, serialization (Owner: the attribute name).** A class or struct field
  marked for saving is written by `std.save` as bytes, versioned by field names
  and a schema hash. It serves save games and is the base of reload migration
  (A7). A field that is not marked is not saved. A reference to another object
  is written once and restored as a reference.
- **D267, suspending code tied to the caller's clock (Owner: the keywords).**
  D260 gave `machine` a `Tick(dt)` that the caller drives. The same idea for
  straight-line code: a `routine` whose body may `wait 2s`, `wait until cond`
  or `wait frame`, compiled to a state machine like `machine`, resumed by
  `Tick(dt)`. Pausing means not ticking; slow motion means a smaller `dt`. No
  host clock hook, no threads.
- **D268, replication attributes (Owner: names and placement).** `replicated`
  fields and `server`, `client` and `multicast` functions are attributes the
  checker validates (an RPC returns nothing, its parameters can be serialized)
  and the reflection API reports (D258). Wolang does no networking; the engine
  maps the attributes to its own policy. This depends on D266 for what
  "serializable" means.
- **D269, a debug protocol.** DAP is already in the compiler
  (`tests/unit/debug`). The host gets it through callbacks, so the engine's
  breakpoint UI can drive a VM: breakpoints, step, locals, call stack. A runtime
  error carries a span and a script stack trace, delivered through the
  reporter. No syntax.
- **D270, sandboxing by capability.** The host denies effects when it loads a
  package (`net`, `fs`, `process`, `unsafe`). A package that uses a denied
  effect fails to load with a diagnostic naming it, because effects are already
  checked statically. Nothing is checked at run time. The question to settle is
  whether `unsafe` can ever be allowed to a mod.
- **D271, a versioned binding ABI.** Generated bindings carry an ABI version and
  a hash of every struct layout they rely on. The loader refuses a mismatch with
  a message. A layout change in the compiler bumps the version. No syntax.
- **D272, AOT without a system `cc` (Owner: the libc choice).** The toolchain
  ships its own linker (LLVM's `lld`) and the runtime archive, and the driver
  calls it directly. On Linux the open point is libc: bundle `musl` and link
  statically, or require the system's C library files without a C compiler.
  macOS and Windows already have fixed linkers. Decide before building.
- **D273, benchmarks.** Calls per millisecond and allocation per call for a
  per-frame script call, in the interpreter, the JIT and AOT, built from
  `benchmarks/actors`. CI records the numbers; `docs/benchmarks.md` publishes
  them. No regression gate in 1.3.0, only the record.

Order: D269, D271, D273 and D270 need no syntax and go first. D265 follows.
D266 comes before A7 and D268. D267 and D272 wait for the owner.

## C. The libraries that were cut

They bind devices and window systems, so each splits in two: the part that is
plain computation, which CI tests headless on every platform, and the part that
needs a device, which answers "no" cleanly when there is none (as `gfx` does,
D247). `gfx` already gives a window, input, pixels, OpenGL and basic sound.

In dependency order:

1. **`font`.** Load a TrueType or OpenType font from bytes, rasterize glyphs
   with an anti-aliased outline fill into an `image`, lay out a line or a
   paragraph (advance, kerning, wrapping), and cache glyphs in an atlas. All
   computation, so all of it is tested headless, including against stored
   reference bitmaps.
2. **`audio`.** A mixer over `gfx`'s sound output: voices, volume, pan, loops, a
   sample-rate converter, and decoders for WAV and one compressed format
   (Ogg Vorbis is the likely one; **Owner**). The mixer and decoders are
   computation and are tested by comparing output buffers. Only the device
   callback needs hardware, and CI covers it where a null device exists.
3. **`ui`.** An immediate-mode toolkit on `gfx` input and `font`: layout, a
   handful of widgets (label, button, checkbox, slider, text field, list), a
   style table, and a draw list. The draw list is data, so layout and hit
   testing are tested headless. Drawing is checked by rendering to an `image`
   and comparing it with a stored one.
4. **`gpu`.** A thin typed layer over the OpenGL context `gfx` already opens:
   buffers, textures, shaders, a pipeline description, draw calls. **Owner:**
   whether this stays OpenGL 3.3 core or becomes an API-neutral layer that can
   later sit on Metal and Vulkan. The first is a month smaller; the second is
   the better long-term shape. CI needs a software GL (Mesa on Linux); macOS and
   Windows runners may not give a context at all, and the plan must say what
   runs where before code is written.
5. **`app`.** The loop that ties it together: window, fixed-timestep update
   driven by `Tick(dt)` (D260), frame pacing, input events, `game.World`, `ui`
   and `audio` set up and torn down in order. It is the first thing a user
   starts a game from, so it comes last and carries the example.

Each library ships a guide section, an example under `examples/`, and an
`Available()` that tells a program whether the device part works.

## D. Self-hosting, stage 1

D250 says tools first, then the lexer and parser. The throwaway lexer
(`tools/selfhost/lexer`) listed nine gaps; this phase closes the ones that block
a real stage 1 and measures the rest.

1. Language and `std` gaps from the lexer, each decided and built or dropped:
   a byte literal (Owner: the spelling), a list literal, braces in text,
   identifier classes and normalization in `std.utf8` (D26), a big integer for
   arbitrary-precision literals (D9), and `Bytes` without `unsafe` now that
   slices are read-only (D251).
2. The `std` gaps from the stage 0 audit: a power-of-two `Map` with a stored
   hash and an optional-returning `Get`, a holdable arena, a bulk copy for
   `Builder`, a stable sort, `List.Insert` and `RemoveAt`, character classes.
   Each is measured by a benchmark before it is changed, because the audit
   read the code and did not time it.
3. The first tool in Wolang, checked byte for byte against the C++ one on
   `lib/`, `examples/` and the docs. The package manager's fetch and lock does
   not need a parser, so it goes first.
4. The real lexer for stage 2, replacing the throwaway one, compared token by
   token with the C++ lexer on every file in the repository and every fuzz
   program.

The stage table puts `fmt` and the doc generator in stage 1, but both need a
parser. Either the tools follow the parser or a token-level `fmt` comes first.
That is an open question below.

## Release gate

`wl ci`, `wl fuzz 200` on two seeds, `wl docs`, and CI green on every platform
(Linux x86-64 and arm64, macOS, Windows x86-64 and arm64) before the PR; the
`asan` preset including `AotTest`; then STATUS.md, CHANGELOG.md and the
wrap-up skill. The PR from `feature/1.3.0` into `alpha` says what was run where
and what was not.

## Open questions for the owner

1. **Scope.** Is every phase in 1.3.0, or do B and C split into 1.3.0 and 1.4.0?
   The libraries are large and the engine decisions are many.
2. **B, syntax.** The attribute name for saved fields (D266), the keywords for
   `routine` and `wait` (D267), and the names and placement of the replication
   attributes (D268).
3. **D272.** Bundle `musl` on Linux, or use the system's C library files without
   a C compiler?
4. **`gpu`.** OpenGL 3.3 core only, or an API-neutral layer from the start?
5. **`audio`.** Which compressed format after WAV?
6. **Sandboxing.** May a mod ever be granted `unsafe` (D270)?
7. **Stage 1.** Parser first, or a token-level `fmt` ahead of it?
8. **Engine headers.** Whether the engine team should confirm the generated
   bindings (items 13, 15, 16, 25) against the real engine headers before 1.3.0
   starts, since 1.2.0 checked them only against their own tests.
